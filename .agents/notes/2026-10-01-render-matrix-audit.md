# 形态矩阵审计：三个只在「组合」上才暴露的缺陷

状态：生效

**类型**：决策记录（问题 / 事实 / 决策 / 替代方案 / 影响）。
**缘起**：维护者要求「确定每一个状态映射的显示样式正确而且万无一失」。逐条读代码查不出来 ——
改成把**宿主真实可能发出的每一组事实**跑完整条链（`severityOf` → `situationOf` →
`presentationOf` → `ringRatioOf`），再看**实际画出来什么**。

## 问题

单测都是「一条判据一行」，而缺陷全在**两条判据的交互**上。三个实例：

1. **账户停用被画成灰环。** `severityOf` 从前先判 `selected === null` → `unknown`。
   而欠费/停用的账户上游**可能给空的 `balance_infos`** —— 那时 `selected` 也是 `null`，
   于是「账户停用」渲染成灰环，与「账户本来就没有余额」**完全同形**。
   判定顺序错了，但两条各自的单测都是绿的（`severityOf(null, false, th)` 当时被断言为 `unknown`）。
2. **`stale` 说了假话。** 「有快照、但快照里一个可展示币种都没有、这轮又没读到」被判成 `stale`
   → 文案「数据已过期」。可用户手里一个数字都没有，那句话听着像「有旧数据可看」。
3. **来源标签的闸门按处境给。** 形态表里有个 `showSource` 开关，表是**按处境**给的，
   而同一处境下「有没有数字」还会变（正是上面第 1 条的 `account-unavailable`）——
   于是会在一份**没有数字**的空浮层里写「（API Key）」。

## 事实

- **第 1 条的根因是判定顺序**：`isAvailable` 必须**先于** `selected === null` 判。
  两条判据各自都「对」，组合起来才错。
- **第 3 条与前一条同源**：`account-unavailable` 在「有余额行」与「空余额列表」两种输入下
  外观完全不同（前者标来源、后者不该标），**一个静态开关表达不了它**。
- **静止态确实有两组「同形」是刻意的**：
  - `critical`（余额恰好为 0）与 `account-unavailable`：都是「红环 + 无叉 + 无弧」——
    红环已经用掉唯一可用的「坏消息」色，两者都要用户去看，靠文案与浮层金额区分；
  - `stale` 与正常的绿/琥珀/红：数字是真的、只是旧，颜色照旧，新鲜度只在文案里说。
  这两组**不是漏改**，写进测试里当断言（改了就红），免得下次被当 bug「修」掉。
- **`ringSpecOf` 成了死代码**：处境重构后没有任何生产调用方，却还有一整组测试在守着它 ——
  那些断言全绿，守的是一个**再也画不到屏幕上**的映射。

## 决策

1. **`severityOf` 里 `!isAvailable` 先于 `selected === null`**，并在注释里写明为什么顺序不能换。
2. **形态表把 `account-unavailable` 的颜色定死为红**（`severityColoured: false`）——
   这是**第二道防线**：即使判定顺序将来被改错，界面也不会把「停用」画成「没信息」。
3. **`stale` 的前提收紧为「真的有一份旧数字」**（`hasSelected`）；没有数字时归 `fetch-failed`
   （说「读不到」才是实话）。
4. **删掉 `showSource`**：来源标签的闸门改成**组件里判 `shown !== null`** ——
   判「这一份数字真的在屏幕上吗」，而不是「这个处境该不该标」。
5. **删掉 `ringSpecOf` 与它的测试**，改为守**不变量**（下面四条），
   并新增 [test/render-matrix.test.ts](../../test/render-matrix.test.ts) 跑端到端矩阵。

**写进测试的四条不变量**（它们比「某个函数返回什么」更能拦住这类缺陷）：

- 返回 `stale` / `ok` / `low` / `critical` ⇒ **一定有可展示的币种**；
- 返回 `account-unavailable` ⇒ 颜色恒红（与 `severity` 无关）；
- **「有数字那一族」的颜色永远不是灰**（灰 = 没信息，不能表示余额高低）；
- 形状通道三分：叉只给「读不到」、＋只给「待配置」、其余无记号。

## 替代方案（想过，为什么不选）

1. **只改判定顺序，不把颜色定死。** 不选：那就是单点依赖 —— 顺序将来被人改回去（它看着很自然），
   缺陷会静默复现。定死颜色是**结构保证**，代价只是一行 `severityColoured: false`。
2. **把 `stale` + 无币种也显示「数据已过期」。** 不选：那是句假话（没有旧数据可看），
   而 `fetch-failed` 的「服务暂不可用」才是实话。
3. **给 `account-unavailable` 加个中心符号以区分「余额为 0」。** 不选：形状通道已经用满
   （叉 = 读不到、＋ = 待配置）；再加一个记号会让并排的三种环互相干扰，
   而这两者的区别**在浮层里一句话就说清了**（「账户不可用」vs 金额 ¥0）。
4. **保留 `showSource` 但改成按「有数字」计算。** 不选：那等于在表里存一个**只能由组件算**的值，
   是重复真相源；直接判 `shown` 更短也更准。
5. **留着 `ringSpecOf` 当「文档性」的映射。** 不选：死代码 + 守它的测试构成**假绿** ——
   看起来有覆盖，实际守着一个到不了屏幕的映射。删掉，改守不变量。

## 影响

- 三个缺陷全部修掉；两条防线各自都有牙齿验证（拆任一条，对应的测试会红）。
- 静止态有两组刻意的「同形」，现在**写在测试里当断言**，不会被误当 bug。
- 代价：判定顺序与颜色定死之间有**一层冗余**（两处都表达「停用 = 红」）——
  这是刻意的，理由见替代方案第 1 条。
- 复盘出的通用做法：**验收界面映射要看「组合」，不能只看单条判据**。
  矩阵测试（[render-matrix.test.ts](../../test/render-matrix.test.ts)）就是这条的落地产物；
  新增处境时必须同时往矩阵里加一行。
