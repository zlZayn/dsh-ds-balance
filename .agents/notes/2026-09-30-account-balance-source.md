# 余额来源：账号登录态作为第二条取数路

状态：生效

**类型**：决策记录（问题 / 事实 / 决策 / 替代方案 / 影响）。
**缘起**：issue #14 第一条 —— 用 DeepSeek 账号登录、没配 API Key 的用户装了插件**看不到任何金额**，因为取数链只认 API Key。

## 问题

取数链是「配置 `apiKey` → `credentials.resolve` → `process.env` → `NoKeyError`」，
而宿主早就有一条不看 API Key 的路（账号登录态的 Platform 查询）。两条路都在官方侧，插件只走了一条。

要一起定的是：**走哪条的规则**、**两个来源怎么不串号**、**新增来源要动多少代码**、**客户端知道多少**。

## 事实（0.2.0-rc.2 复核）

- 宿主账号服务 `ctx.deepseekAccount`：`getState()`（`credential-stored` = 已登录）、`getBalance(client)`
  （`/api/v0/users/get_user_summary` 的 `normal_wallets` + `bonus_wallets`，失败是 `status: 'failed'` 而不是零余额）、
  `getPlatformSession()`（**不发请求**就能拿到 `userId` —— 稳定账号 id，来自同一份 grant 的 profile 读取）。
- 两条模型路由的 provider id 是分开的：`deepseek-official`（Key 适配器）与 `deepseek-account`（账号适配器）。
- 会话级模型选择是**会话投影**（`modelSelection`，`next` 为空才回落全局默认）；
  客户端壳层的侧栏不在会话作用域里，要自己读。
- 存储域规则：**域版本与 spec 不一致时 open 直接 `version-mismatch` 拒开** —— 抬版本等于让旧账本打不开，
  所以取值的扩展只能「只增不改」。
- npm 三条线上都有 `@deepseek-ai/dsh-deepseek-account-platform`（不与 plugin-manager 那个「某条线没版本」的坑同形）。

## 决策

1. **四层回落**：当前会话的路由 → 全局默认路由 → 固定顺序（**Key 优先**，账号兜底）→ 一条都没有就回 Key 那条账本自然报 `NO_KEY`。
   Key 优先是刻意的：**绝不改变今天能用的用户看到的数字**。
2. **两条路各持一份账本**：快照、状态、失败退避、手动冷却都独立；门面只决定「这一轮谁活跃」。
   调度刷活跃来源，不重新解析（否则会话级的来源会被全局默认无声顶掉）。
3. **不串号**：账号账本的派生输入是 `account:<userId>`（HMAC 前 32 hex），与密钥那条的键空间用前缀分开；
   快照仍按 `accountTag` 落盘、按 tag 读回，两条路因此永远不会混进同一个账本。
4. **新增一个来源只动一处逻辑**：`source-selector.ts` 加一行 `ROUTED` + 排进 `FALLBACK_ORDER`，
   装配处多一份 reader 与账本。账本状态机、调度、HTTP、界面都不认识具体来源。
5. **客户端只知道两件事**：响应里的 `source`（用来出括号标签）与当前会话的 provider id（当提示带上）。
   选源规则、凭据链、账本语义全在宿主侧 —— 客户端不判断「该用哪条」。
6. **界面标签**：标题**右边**跟一个括号标签（`（API Key）` / `（账号登录）`），
   与标题合成一组占左端（这一行是 space-between 的两端布局，三个并列子元素会把标签推到行中间）。
   **括号属于词典**（中文全角、英文半角带空格），代码只做拼接；`state.noKey` 改成凭据中立措辞。
7. **声明面**：按本仓依赖判据第二条（消费它提供的服务 → 必须 peer），
   `@deepseek-ai/dsh-deepseek-account-platform` 进 `peerDependencies`（+ 同版本 dev），运行时仍用 `ctx.inject` 把门降级。
8. **存储只放宽枚举、不抬域版本**：`source` 从 `z.literal('deepseek-http')` 放宽成 `z.enum([...])`。
9. **展示 / 刷新 / 标签必须指同一条**：哪条把数字交出去，`active` 就是哪条（`mark(served)`）——
   展示账号的数字、标签就写「账号登录」、调度与手动刷新也刷账号。三者分家的界面是「精神分裂」。
10. **本插件只记官方那一个**，所以首选那条拿不出数字时**退到另一条官方路**：一条有旧快照、另一条没有 → 显示旧快照；
    **两条都拿不出数字才画叉**（那才是「没接入官方」）。
11. **兜底的代价封顶**：一轮最多「首选一次 + 兜底一次」，按固定顺序走一遍就停 —— 不来回重试（ping-pong）。
12. **「没接入」与「接入了但出错」分开**：前者没信息可画 → 空环 + 「尚未配置凭据」；
    后者账户读不到 → 叉 + 「服务暂不可用」。旧的「无快照一律空环」会让两种完全不同的处境长得一样。

## 替代方案（想过，为什么不选）

1. **账号优先**（登录态盖过环境变量里的 Key）。不选：这台机器就是「两个都有」的样本 —— 数字会悄悄换成另一个号，且没有任何解释。
2. **给账号一个合成常量 tag**（issue 里提的）。不选：宿主已经给了稳定账号 id，用常量等于白白放弃「换账号就换账本」。
3. **按主模型供应商自动推导**（原第 ④ 条）。不选：那是把 DeepSeek 的钱贴上别家的标签；方向被 issue 作者自己推翻。
4. **加一个「取数来源」配置字段**。不选：多一个字段、多一个选项，只服务「两个都有还想切」的极少数；真要切，把二级折叠里的凭据引用名改成不存在的名字即可断掉 Key 那条链。
5. **客户端自己读会话投影并决定来源**。不选：选源要问三条路的可用性（凭据在宿主侧），客户端知道得越少越好 —— 它只当提示的搬运工。
6. **抬域版本号做迁移**。不选：`version-mismatch` 会让用户已落盘的账本直接打不开；这次是**放宽**（旧记录仍合法），不需要迁移。

## 影响

- 登录态用户从「装了看不到」变成「正常显示」；Key 用户在两个来源都可用时**数字一字不变**。
- 界面多一个来源标签；`state.noKey` 从「尚未填写 API Key」改成凭据中立措辞（两种来源下都不再说错话）。
- 已知边界：宿主本进程还没读过 profile 时账号 id 拿不到，退回 `account:unknown`（那种情况下换账号不换账本，下一轮抓取自愈）；
  同一会话内改模型要等下一轮轮询才跟上（会话投影的订阅面不保证存在，而切会话能立刻跟上）。
- 指标键带上 `source` 标签；healthz 多一个 `source` 字段，两条路并存时一眼能看出服务的是哪条。
