# 声明下限 vs 实际运行版本：一次「裸引新 token」的排查

状态：被取代

指针：[承诺线从 alpha 换到 RC 线（dist-tag 是 `next`）](2026-10-01-track-rc-line.md)
—— 本文的结论（保 `>=0.1.7-alpha.1` + 为 token 写回落值）已随换线反转；正文保留作当时的依据。

**类型**：决策记录（问题 / 事实 / 决策 / 替代方案 / 影响）。
**缘起**：本轮把圆角与焦点环改用官方语义 token（`--dsw-radius-*` / `--dsw-focus-ring-*`），排查中发现**这两族 token 比本仓声明的下限晚三个版本才存在**。

## 问题

本仓 `engines.dsh` 与 23 处 `peerDependencies` 都声明 `>=0.1.7-alpha.1`。
本轮引用的 token 若在那个版本里不存在，`var()` 会**静默失效**：

- `border-radius: var(--dsw-radius-lg)` → 圆角退化成 **0**（方角）；
- `outline: var(--dsw-focus-ring-width) solid …` → `outline-width` 变 **0**，**焦点环整条消失**（无障碍回归，且不报错）。

两者都不会让编译或测试变红 —— 属于「只有真机看得见」的那一类。

## 事实（逐条实测）

- **token 是宿主 0.1.7-rc.2 才进的**（`ui-theme/src/styles/base.css` 与 `focus.css`）。
  逐 tag 查：alpha.1 / alpha.2 / rc.1 三档**零命中**，rc.2 起才有。
- **装的那份与在跑的那份不是一条线**：本仓 `node_modules` 装 `0.1.7-alpha.1`（声明下限那一档），
  而**在跑的宿主是 `0.2.0-rc.1`**。所以「照着 node_modules 里的官方 CSS 抄」会抄到老线的写法。
- **两条线上官方的值本身就不同**，不是「同一个值的两种写法」：

  | 官方规则 | 0.1.7-alpha 线 | 0.1.7-rc.2 起 |
  |---|---|---|
  | `stat-dialog.panel` 圆角 | `12px` | `var(--dsw-radius-lg)` = 16px |
  | `SidebarRoot.iconButton` 圆角 | `50%` | `var(--dsw-radius-sm)` = 8px |
  | `LanguageRow.selector` 圆角 | `18px` | `var(--dsw-radius-md)` = 12px |
  | `:focus-visible` | `outline: 2px solid <具体 token>` | `--dsw-focus-ring-width/-color` |

  所以**回落值不是「token 值的安全近似」，而是「老线上官方的值」** —— 两者在 h36 pill 那一档
  恰好不同（18 vs 12）。
- **`>=0.1.7-rc.2` 是一个死区间**：npm 的 semver 预发布规则下，`>=0.1.7-rc.2` **只**匹配
  `0.1.7-rc.2` 及以上同 `major.minor.patch` 的预发布版 —— 实测 `0.2.0-rc.1` / `0.2.0-rc.2`
  **都不满足**它。而没有任何 dist-tag 指向 `0.1.7-rc.x`（alpha=0.1.7-alpha.2、next=latest=0.2.0-rc.2）。
  **提下限到 rc.2 会同时漏掉「承诺线」与「本机在跑的宿主」，比两个极端都差。**
- **承诺线是 `alpha`**：README 的「版本兼容」一节让用户装 `@deepseek-ai/dsh@alpha`
  （= `0.1.7-alpha.2`），`scripts/check-declaration.mjs` 的 `TRACKED_LINE` 就是 `alpha`，
  每周 CI 判「声明罩不罩得住这条线」。

## 决策

**保 `>=0.1.7-alpha.1`，并为这两族 token 全部写回落值**（回落值 = 该组件在老线上官方的值）。

三条理由：

1. **回落值让声明成真，不是「为兼容而兼容」**。声明写着罩住 alpha 线，而那条线上官方写的是
   `12px` / `50%` / `18px` 字面量。没有回落，代码在老线上渲出的形状**与声明里的承诺不一致**；
   有了回落，同一个 `var()` 在两条线上各自得到**那条线上官方的值**。
2. **提出来的那个区间（rc.2）是死的**（见上）。真要提，只能提 `>=0.2.0-rc.1`。
3. **提到 `>=0.2.0-rc.1` 是产品承诺的变更，不是 CSS 迁移的一部分**：它会让
   `check-declaration` 对 `alpha` 线变红、要同批改 README 的安装指引与 CI 的 `TRACKED_LINE`。
   那是「换承诺线」这件事，该在正式采纳 0.2 线时做，不该被一次样式改动顺手带走。

**回落值的口径写进代码注释**（每一处都写了「老线官方值是什么」），并由
`test/redlines.test.ts` 的三条断言守着：值必须等于老线官方值、不许裸引、安装面不得低于下限。

## 替代方案（想过，为什么不选）

1. **提下限到 `>=0.1.7-rc.2` 并删回落。** 不选：**它是死区间** —— 只匹配 `0.1.7-rc.x`，
   而三条 dist-tag 线没有一条指向那里；实测会同时漏掉承诺线（alpha.2）与本机在跑的宿主（0.2.0-rc.1）。
2. **提下限到 `>=0.2.0-rc.1` 并删回落。** 合理但**是另一件事**：它覆盖在跑的宿主与 next/latest，
   却让承诺线落空（`check-declaration` 变红），必须同批改 README 的「装 @alpha」指引与
   `TRACKED_LINE`。留作**采纳 0.2 线时的那一步**，记录在此备查。
3. **`>=0.1.7-alpha.1 || >=0.2.0-rc.1`（两段都罩）。** 想过：能同时罩住两条线，
   但**回落值一样省不掉**（老线仍然缺 token），只是让声明更啰嗦 —— 没有买到任何东西。
4. **不引 token，继续写死像素。** 不选：那就得在两套值之间选一套，等于主动放弃另一条线；
   而 token 化本来是「官方改值我们自动跟」的收益来源。
5. **把 token 也抄进本仓的 CSS 变量定义（`--dsw-radius-lg: 12px` 之类）。** 不选：
   那是在本仓复制官方刻度，官方一改就静默漂开 —— 与「只有一个真相源」相冲；
   而且我们的 `--dsw-*` 定义会与宿主的同名变量打架。

## 影响

- 圆角与焦点环在**两条宿主线上各自等于那条线官方的值**；零回归（老线仍是老线的形状）。
- 代价：每处回落多一个参数、每处注释要写清「老线官方值是什么」。已由红线兜住，不会烂。
- **一般化的一条规则**（本轮真正的产出）：**引任何官方东西之前，先确认它在声明下限那一档存在**
  ——包括 token、组件的 prop、导出的符号。存在性检查之外还要看**值是否在两条线上相同**：
  不同就必须 token + 回落，且回落值取**老线官方的值**。
- 反转时机：宿主 0.2 线成为承诺线（README 改指 `@next` / `@latest`、`TRACKED_LINE` 同步）时，
  把下限提到 `>=0.2.0-rc.1`、删掉这些回落值，并把本条状态改为「被取代」。
