# 边界记录：来源切换提示不做、失败态轮询会穿透、凭据改动等一轮

状态：生效

**类型**：决策记录（问题 / 事实 / 决策 / 替代方案 / 影响）。
**缘起**：处境重构（环 / 文案 / 标签统一从「处境」派生）定稿时，维护者要求把**刻意不做**的几件事
与**已知边界**一并记下来，免得它们被当成漏改。

## 问题

处境重构会碰到三处「用户可感知但本轮不改」的行为。不写下来的后果：下次有人看到这些现象，
会以为是重构没做干净，然后顺手「修」掉其中某一条（而每一条都有不修的理由）。

## 决策

### 1. 来源在两条官方取数路之间切换时，界面**不给任何提示**

- 保留 `mark()` 的一笔 debug 日志（`balance source switched`）。
- 理由：正常路径下切换是**静默且正确**的 —— 标签与数字同时换、两者始终一致；
  需要提示的场景只有「两条路都时好时坏导致来回摆」，那是异常态，为它加提示等于给所有人加噪音。
- 已知代价：来源摆动（数字在两个钱包之间跳）对用户**不可见**，只能看日志。

### 2. 失败态下客户端轮询会穿透上游 —— 已知边界，本轮只改文案

- `canServeCache()` 要求 `state === 'ok'`，所以首选来源不是 `ok` 时（stale / error）
  **每次** `getView` 都真打一次上游，而它不读退避与 `Retry-After`。
- **这是既有取舍，不是漏改**：[2026-09-30-refresh-timing-single-clock.md](2026-09-30-refresh-timing-single-clock.md) 的替代方案第 5 条
  已经讨论过「让 GET 永不触发抓取」，结论是本轮不动；那一轮还明写「缓存不可服务时轮询代打
  **正是恢复可见性的来源**」。
- 本轮只做一件事：**把说反了的文案改对** —— 配置项 `clientPollSeconds` 的说明
  （`settings.hint.clientPollSeconds`）与组件注释都写着「只读本地缓存，不访问上游」，
  这在失败态是假话。
- 留给下一次决策：要不要改成「GET 永不抓取、上游只留一个节拍器」。改了是契约变更
  （§8 写的是「过期则抓」），要单独记账。

### 3. 凭据改动（非空 → 非空）不立刻重取，最多等一轮轮询

- 客户端配置指纹刻意**不含密钥本身**，只带一个「配没配」的布尔（密钥不进 React 依赖串）。
  所以把 Key 从 A 换成 B（两者都非空）不会改变指纹，客户端不会立刻重问。
- 宿主侧 `apiKey` 在 `SCHEDULE_FIELDS` 里，会立刻 `scheduler.reset()` 抓一轮；
  客户端最多晚一个轮询周期（≤ `clientPollSeconds`）看到。
- 口径与 [2026-09-30-credential-change-refresh-boundary.md](2026-09-30-credential-change-refresh-boundary.md) 一致（凭据变更「等下一个刷新周期」）。
  **不改**：让密钥进依赖串的代价（把明文带进 React 的依赖比较与潜在日志）高于这点延迟。

## 替代方案（想过，为什么不选）

1. **切换时弹一次 toast。** 不选：频率不可控（正常兜底也会触发），且 toast 会盖住浮层。
2. **浮层里加一行「当前数据来自账号登录」。** 不选：与已有的来源括号标签重复。
3. **标签加过渡动画。** 不选：只掩盖事实，不给信息。
4. **给失败态加客户端退避。** 不选：那是行为变更（会拖慢恢复可见性），该与「GET 是否抓取」
   一起决策，不该顺手做。
5. **把 `apiKey` 放进配置指纹。** 不选：见第 3 条。
6. **删掉 `clientPollSeconds` 的说明文字。** 不选：用户需要知道这个字段管什么；
   正确做法是把「不访问上游」改成有条件的说法。

## 影响

- 三处都成为**可查的已知边界**，不再需要靠读代码判断「这是不是 bug」。
- 第 2 条的文案修正让界面不再说假话；行为不变。
- 观测出口：第 1 条的摆动此前完全不可见，本轮补了
  `balance_source_switch_total{from,to}` 计数器（`/api/v1/healthz` 的 `metrics` 段可读），
  让「来源在摆」从只能翻日志变成可查。
- 反转任一决策时：新写一条记录并把本条状态改为「被取代」。
